# PRD:動態步態分析 (Gait Analysis)

> 狀態:已定案 · 實作階段 P0
> 最後更新:2026-08-06

---

## 1. 背景與問題

現有產品是**靜態體態分析**:使用者上傳正面與側面兩張照片,由 Gemini 從影像「目測」估出各項角度數值。這個做法有兩個本質限制:

**數據不可信** — `headTiltAngle`、`pelvicTiltAngle` 等數值是大型語言模型從單張影像猜出來的。同一張照片重跑兩次可能得到不同數字,沒有可重現性,也無法寫測試驗證。使用者無從判斷「肩膀高低差 1.2 cm」這個數字是量出來的還是編出來的。

**看不到動態代償** — 許多臨床上重要的問題只在**行走時**才顯現:髖外展肌無力造成的骨盆下沉、踝背屈受限造成的代償性步態、疼痛造成的患側站立期縮短。靜態站姿完全看不出來。

步態分析的價值在於:走路是高度重複的循環動作,可以量化出**客觀、可重現、左右可直接比對**的運動學指標。

## 2. 目標

| 項目 | 內容 |
|---|---|
| **主要目標** | 使用者上傳一段走路影片,得到客觀量化的步態指標 + AI 臨床解讀 + 個人化運動處方 |
| **成功指標** | 同一人相同條件重複拍攝 3 次,核心指標(步頻、對稱性指數)變異係數 < 10% |
| **非目標** | 醫療診斷、實驗室級精度(需力板與多鏡頭動作捕捉)、跑步分析、即時回饋 |

## 3. 已定案的四項決策

| 決策點 | 選擇 |
|---|---|
| 分析引擎 | **雙軌交叉驗證** — MediaPipe 演算法軌 + Gemini 影像理解軌並行 |
| MVP 輸入 | **只做影片上傳**(不做 App 內即時錄影) |
| 功能定位 | **步態完全取代靜態姿勢分析** |
| 資料保存 | **影片不上傳雲端**,只存指標與關鍵幀 |

## 4. 核心架構:雙軌交叉驗證

```
影片(端上)
   │
   ├──► [A 軌] MediaPipe PoseLandmarker 逐幀 33 關節點
   │              ↓ 純演算法,無 AI,可寫單元測試
   │        gaitMetrics.ts
   │          · 移動平均濾波
   │          · Zeni 步態事件偵測(觸地/離地)
   │          · 關節角度時序 → 步態週期正規化 (0-100%)
   │          · 時空參數 + 對稱性指數
   │              ↓
   │        客觀指標 JSON
   │              │
   └──► [B 軌] Gemini 獨立觀看取樣關鍵幀 ─────────┐
                  · 獨立估計步頻與對稱性印象      │
                  · 質性觀察(表情、衣物、地面)  │
                  · 不知道 A 軌的任何結果          │
                                                   ▼
                                    [仲裁層] reconcileTracks()
                                      純程式計算兩軌數值一致性
                                                   ↓
                          Gemini 最終報告(以 A 軌數據為準)
```

### 為什麼要雙軌

單軌管線最大的風險是**靜默失敗**:當關節點被抓錯(衣物寬鬆、背景雜亂、光線不足),演算法仍然會吐出一組看起來合理的數字,使用者無從察覺。

雙軌的價值在於 B 軌是**完全獨立的觀測**。兩軌對步頻的估計若差異超過 15%,幾乎可以確定其中一軌出了問題 → 系統主動提示「本次拍攝條件可能不佳,建議重拍」,而不是給出一份錯誤但看起來很專業的報告。

### 職責分工

- **A 軌為準**:所有數值一律採用 MediaPipe 演算結果。Gemini 不產生任何最終數字。
- **B 軌為輔**:提供 A 軌算不出來的質性觀察 — 是否面露痛苦、衣物是否遮蔽關節、鞋子是否合適、地面是否平整、是否使用助行器。
- **仲裁層為純程式**:一致性比對用 TypeScript 計算,不交給 AI 判斷。

### B 軌的輸入格式

不傳送完整影片,而是**均勻取樣 14 張關鍵幀**送給 Gemini。理由:

- 瀏覽器端做影片轉碼壓縮複雜且不穩定,取樣影格用 canvas 即可完成
- token 用量可精確控制與預測
- 14 幀跨越 2-3 個完整步態週期,足以讓 Gemini 判斷節律與對稱性

## 5. 量化指標清單

### 時空參數 (Spatiotemporal)

| 指標 | 說明 | 正常參考 |
|---|---|---|
| 步頻 Cadence | 每分鐘步數 | 100–120 steps/min |
| 步態週期時間 | 同側連續兩次觸地間隔 | 1.0–1.2 s |
| 站立期佔比 | Stance phase % of cycle | ~60% |
| 擺盪期佔比 | Swing phase % of cycle | ~40% |
| 雙支撐期佔比 | Double support % | ~20% |
| 步長 Step Length | 左右腳觸地時的前後距離 | 0.6–0.8 m |
| 步幅 Stride Length | 同側連續觸地距離 | 1.2–1.6 m |
| 步行速度 | 步長 × 步頻 | 1.2–1.4 m/s |
| 步寬 Step Width | 需正面視角 | 0.08–0.12 m |
| 步態週期變異度 | Stride time CV,反映節律穩定性 | < 3% |

### 運動學參數 (Kinematics)

輸出**整個步態週期 0–100% 的角度曲線**(每側各 101 點,跨週期平均):

- 髖關節屈伸角度 + ROM(正常 ~40°)
- 膝關節屈伸角度 + ROM(正常 ~60°)
- 踝關節背屈/蹠屈角度 + ROM(正常 ~25°)
- 擺盪期最大膝屈曲角(正常 ~60°)
- 觸地時膝屈曲角(正常 0–5°)
- 軀幹前傾角、軀幹左右擺動幅度
- 骨盆傾斜角度與單腳站立期下沉量(Trendelenburg 徵象)
- 手臂擺動 ROM 與左右對稱性

### 對稱性

```
對稱性指數 SI = |左 − 右| / (0.5 × (左 + 右)) × 100%
```

套用於:步長、步態時間、站立期佔比、髖/膝/踝 ROM、手臂擺動 ROM。

**這是最有臨床意義、也最不受單鏡頭校正誤差影響的指標** — 因為左右兩側共用同一組校正參數,誤差會相互抵消。

### 異常樣式偵測

由指標推導(程式判定)+ Gemini 判讀(質性佐證):

- 疼痛跛行 Antalgic gait — 患側站立期顯著縮短
- Trendelenburg 步態 — 單腳站立期對側骨盆下沉 > 5°
- 環行步 Circumduction — 擺盪期膝屈曲不足 + 骨盆上提
- 垂足步 Steppage — 擺盪期踝背屈不足 + 代償性髖膝過度屈曲
- 小碎步 Shuffling — 步長顯著偏短 + 步頻偏高 + 踝 ROM 偏低
- 膝過度伸直 Genu recurvatum — 站立期膝角度為負
- 內八 / 外八 — 足前進角異常(需正面視角)

## 6. 使用者流程

1. **輸入身高**(尺度校正必需,必填)
2. **拍攝引導**:手機橫放固定於腰部高度 · 距離 3–4 公尺 · 側面走過鏡頭 · 來回 2 趟 · 貼身衣物 · 光線充足 · 全身入鏡
3. **上傳側面影片**(必填)· **選填加上一段正面/背面影片**以解鎖步寬、Trendelenburg、軀幹側擺
4. **端上分析**:逐幀 pose 推論,顯示進度(已處理 X / Y 幀,兩段影片依序處理)
5. **雙軌比對**:顯示量測信心度
6. **結果報告**:總分 → 信心度 → 時空參數 → 對稱性 → 關節角度曲線 → 異常樣式 → AI 臨床解讀 → 改善建議
7. **教練模式**:沿用現有實作,運動處方改由步態問題驅動

### 相依套件

新增 `@mediapipe/tasks-vision`。WASM 與模型檔預設走 CDN,可用環境變數覆寫為自架路徑:

- `VITE_MEDIAPIPE_WASM_PATH`
- `VITE_POSE_MODEL_URL`

### 尺度校正

MediaPipe `worldLandmarks` 已是公尺級座標(以髖中心為原點),但採用的是「平均體型」假設。以使用者實際身高再校正一次:

```
推估身高 = (踝中點 − 鼻尖) 垂直距離 / 0.891
校正係數 = 實際身高 / 推估身高
```

`0.891` 為人體測量學常數(鼻高 ≈ 0.930 × 身高,踝高 ≈ 0.039 × 身高)。校正係數若偏離 1.0 超過 ±40%,判定為姿態偵測異常並降低信心度。

### 步態事件偵測

採用 **Zeni et al. (2008) 座標法**,矢狀面視角下最穩健的無標記點方法:

- 觸地 (Heel Strike) = 足跟相對骨盆的**前向位移極大值**
- 離地 (Toe Off) = 足尖相對骨盆的**前向位移極小值**

使用 world 座標(髖中心為原點)可自然消除人體在畫面中的整體平移,不需額外處理相機視差。

### 資料保存

- 影片以 `URL.createObjectURL` 端上讀取,分析完成後 `revokeObjectURL` 釋放
- B 軌送出的取樣影格為單次請求用完即棄,不落地
- Firestore 每筆記錄:指標 JSON + 降採樣角度曲線(101 點)+ 2–4 張 < 100 KB 關鍵幀 + 雙軌一致性報告,目標單筆 < 400 KB
- `history` collection 新增 `type: 'posture' | 'gait'` 欄位
- `firestore.rules` 的 `isValidAnalysis()` 需改寫以同時接受兩種 schema

### 舊資料處理

使用者雲端既有的 posture 記錄**保留為唯讀**,不刪除。歷史清單以 `type` 欄位區分,舊記錄仍可點開檢視,只是不再能產生新的靜態分析。產品改版不應連帶清空使用者已累積的資料。

## 8. 已知限制(需明確揭露給使用者)

- **單鏡頭 2D**:絕對距離靠身高推估,步幅誤差可能達 10–15%。**對稱性與角度指標較可靠,絕對長度僅供參考**
- **拍攝條件敏感**:需全身入鏡、光線充足、貼身衣物,否則關節點偵測品質下降
- **處理時間**:10 秒 30 fps ≈ 300 幀,中階手機約需 6–10 秒
- **矢狀面優先**:核心時空參數(步頻、步長、關節角度曲線、左右對稱性)仍以側面影片為準。步寬、Trendelenburg、軀幹側擺需要額外上傳一段正面/背面影片(選填)才能量測;足前進角(內外八)尚未實作,留待 P1。
- **不具醫療診斷效力**,免責聲明需強化並置於顯著位置

### 8.1 正面視角補充分析(P0 內追加)

原規劃將正面視角指標排入 P1,但因步寬、Trendelenburg、軀幹側擺三項在臨床上判讀價值高且實作成本遠低於預期,已提前納入 P0:

- 使用者可在上傳側面影片之外,**選填**再上傳一段「面對或背對鏡頭直線行走」的影片
- 這段影片不影響側面影片算出的任何數值(步頻、步長、關節角度曲線、對稱性),兩者互不干擾
- 步寬、骨盆下沉、軀幹側擺的計算不需要步態事件偵測(不需要 Zeni 演算法),只需身高校正 + 逐幀的髖/肩/踝側向座標,因此不必複製一整套側面影片的分析管線
- `GaitQuality.frontalSource` 標記這三項數據的來源:`'supplement'`(獨立正面影片)、`'primary'`(側面影片恰好帶正面角度)、`'none'`(未量測)
